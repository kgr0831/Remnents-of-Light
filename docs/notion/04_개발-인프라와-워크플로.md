## 📱 디스코드 원격 개발 시스템

휴대폰에서 슬래시 커맨드 하나로 노트북의 Claude Code를 돌리는 구조. 외출 중에도 개발이 진행된다.

```
[휴대폰 디스코드]
      │ 슬래시 커맨드 / 승인 버튼 / 답장
      ▼
relay_bot.py      dishost.kr 상시 배포 (게이트웨이·슬래시커맨드 소유)
      │ #claude-queue 채널에 "CMD: {...}" 적재 (디스코드 자체를 큐로 재사용)
      ▼
executor.py       노트북 상주, REST 폴링(3초), claude -p 헤드리스 실행
      ▼
claude_bridge.py  allowedTools 프로필 · 프리앰블 · 트랜지언트 재시도
      ▼
discord_bot.py    순수 REST 클라이언트
```

### 슬래시 커맨드 6종

| 커맨드 | 용도 |
| --- | --- |
| `/claude` | 읽기 전용 질답 |
| `/claude-loop` | 개발 작업 (루프 모드) |
| `/claude-auto` | 기획안 + task.md를 보고 **다음 작업을 스스로 결정** (승인 1회) |
| `/claude-memory` | 영구 기억 저장 |
| `/claude-fix` | 이 시스템 자체를 수정 |
| `/claude-stop` | 즉시 중단 |

### 안전 게이트

- `--allowedTools` 화이트리스트로 헤드리스 호출의 도구를 제한 (대화형 세션엔 영향 없음)
- 목록 밖 작업 · 사람의 판단이 필요한 선택지는 전부 **`NEEDS_APPROVAL:`** → 디스코드 질문
  (버튼 또는 답장) → `--resume`으로 세션을 이어서 재개
- 선택지는 **항상 숫자 목록** (A/B/C 금지 — 답장 매칭용)

### 운영 특성

- **FIFO 큐** — 연달아 보내도 순차 실행, busy 중 요청도 유실 없음
- **오프라인 감지** — heartbeat 60초 갱신, relay가 180초 신선도 체크
- **부팅 자동 시작** — 작업 스케줄러 `RemnentsOfLight-Executor` (`pythonw.exe`, 콘솔 창 없음)
- **트랜지언트 재시도** — 529/503/rate_limit 감지 시 15초 대기 후 최대 3회

## 🎬 영상 검증 파이프라인

**코드 변경이 있었던 완료 작업은 영상 보고가 필수다.** 텍스트만으로는 "정말 되는지" 확인이 안 되기 때문.

```
TestRecorder.StartRecording("<기능>_<날짜>")
      ▼  (Play 모드 검증 구간)
StopRecording() ──▶ Recordings/*.mp4
      ▼
report_video.py ──▶ YouTube 업로드(OAuth2) + AI 영상 판단
      ▼
stdout: URL: ... / VERDICT: PASS|FAIL (n/m)
      ▼
DONE: 블록에 실려 디스코드로 보고
```

> ⚠️ **`TestRecorder`가 켜져 있으면 실측 1.5fps로 떨어진다.**
> Unity Recorder가 `captureDeltaTime`을 1/30으로 고정하고 1280×720 MP4를 프레임마다 인코딩하기 때문.
> **게임 시간 9초 테스트가 실시간 3분**이 된다 → 녹화 시나리오는 10초 이내로 짤 것.

## 🧪 `[ASSERT]` 검증 규약

성공 기준을 로그 한 줄로 못박고, 통과할 때까지 반복하는 것이 이 프로젝트의 기본 작업 방식이다.

```
[STEP]   <channel>: 무엇을 하는 중
[ASSERT] <channel>: PASS a=1 b=True
```

- 규약 문서: `docs/dev/ASSERT_CONVENTION.md` (채널 목록 표를 **먼저** 갱신하고 코드를 짠다)
- 구현: `Assets/Scripts/TestLog.cs`
- 시나리오: `Assets/Scripts/Testing/PlayTestRunner.cs` → `Tools/PlayTest/*` 메뉴로 노출
- 입력 주입: `Assets/Scripts/Testing/InputInjector.cs`

### 채널 목록 (일부)

`dash_iframe` · `dash_vfx` · `dash_afterimage_shape` · `dummy_damage` · `dummy_attack` · `ilseom` ·
`combo_window` · `parry_timing` · `execution` · `player_damage` · `game_data` · `ego` · `light_pixel` ·
`rampage_vision` · `state_entry_defer` · `trap_crumble` · `trap_press` · `time_accel` · `wall_climb_gate`

### 테스트 설계 원칙 (실패로 배운 것들)

| 원칙 | 왜 |
| --- | --- |
| **판정값을 하드코딩하지 말고 `player.<필드>`에서 읽어라** | 튜닝값이 바뀌어도 테스트가 따라간다 |
| **음성 판정("움직이지 않음 = 통과")을 경계하라** | 기능이 아예 안 걸려도 통과한다. 기대하는 **EVENT 로그가 실제로 찍혔는지**를 함께 본다 |
| **기준선(baseline)이 비정상이면 `SETUP_FAILED`로 못박아라** | 벽에 막혀 dist=0.000인 걸 "통과"로 읽으면 안 된다 |
| **씬 지형에 기대지 말고 런타임 전용 테스트 지형을 세워라** | 씬 파일을 안 건드리고도 원하는 형상을 정확히 만들 수 있다 (끝나면 파괴) |
| **적을 쓰는 시나리오는 `enemy.moveSpeed = 0` + 알려진 좌표** | 추적하게 두면 발동 거리가 매번 달라진다 |
| **결정적 검증 전엔 stop → play로 새 세션을 강제하라** | 이어진 세션에서는 이미 끝난 공격의 회수 구간이 섞여 비결정적으로 FAIL한다 |
| **대조 실험으로 인과까지 확정하라** | 고쳤더니 PASS ≠ 원인이 그거였다. 옛 값으로 되돌리면 FAIL이 재현되는지 확인 |

## 🔌 MCP for Unity

에디터를 원격에서 조종하는 주 수단. **주력 무기는 `execute_code` + 리플렉션 직접 검증**이다.

- 원격/비포커스 에디터는 프레임 스로틀이 심해 **실시간 코루틴 테스트의 신뢰도가 낮다**
  → `HandleAttack()` / `anim.Update()` 를 직접 순서대로 호출하는 **결정적 테스트**로 전환
- `read_console`은 **warning/error만** 반환한다 → `[ASSERT]` 로그는 `Editor.log`를 직접 grep
- `unity_reflect`(get_type/get_member)가 문서보다 확실하다 — 로드된 실제 어셈블리를 본다

## 🎯 작업 모드 규약 (`.claude/CLAUDE.md`)

| 모드 | 게이트 |
| --- | --- |
| **대화 모드** (기본) | 매 단계 사용자 허가 |
| **루프 모드** | 허가 대신 **검증 통과**가 게이트. 한 번에 태스크 하나. 같은 검증 3회 연속 실패 시 중단 |

두 모드 공통으로 **파괴적 작업**(삭제 · git commit · 리팩터 · 씬/메타/tmx 직접 편집)은 **반드시 질문**한다.
그래서 이 프로젝트의 상당수 기능이 **"에셋 편집 0건, 코드만으로"** 구현돼 있다 —
런타임 Canvas 절차 생성, `Shader.Find` 재사용, `Keyboard.current` 직접 폴링 등이 전부 그 결과물이다.
