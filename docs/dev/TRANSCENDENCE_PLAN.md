사용자 지시(2026-08-02) 원문:
> "광원이 100%일 때 발동되어, 70%가 될 때까지 유지되며 초월상태가 유지되는 동안 마스킹 시트에 따른
> cyan 색상 블룸이 플레이어에게 적용됩니다.(폭주 시스템의 블룸과 색상만 다름.) 또한 이제 적의 미래
> 공격 범위를 시각화 하여 볼 수 있게 됩니다."

### 이 계획의 핵심 판단: **새로 만들 것이 거의 없다**

초월은 폭주의 **정확한 반대 대칭**이고, 필요한 부품이 전부 이미 있다.

| 필요한 것 | 이미 있는 것 | 이번 작업 |
|---|---|---|
| cyan 마스크 블룸 | `Custom/PlayerMaskEmissive` + `PlayerBloomFx.AttachWithShader` — 폭주가 `RampageBloomTint`로 구동 중 (`PlayerController.cs:1449~1467`) | **색·세기만 다르게 호출** (신규 셰이더 0) |
| 100% 진입 / 70% 해제 | 폭주의 이력(hysteresis) 상태 머신 (`PlayerController.cs:1309~1324`) | 부등호를 뒤집어 복제 |
| 정수 자원의 소수점 드레인 | `rampageDrainAccum` · `egoDrainAccum` · `lightSpendDrainAccum` 누적 패턴 | 같은 패턴 1개 추가 |
| 적 공격 판정 원의 위치·반경 | `DummyEnemy.AttackHitPoint` · `AttackHitRadius` — **이미 public** (`DummyEnemy.cs:325~327`) | 그리기만 하면 됨 |
| 적 단위 VFX 부착·컬링·페이드·누수 방지 | `RampageVisionFx.ScanEnemies()` (12유닛 컬링, 0.25s 스캔, `OnDestroy` 정리) (`RampageVisionFx.cs:137~166`) | 구조 복제 |
| 발광 마스크 14장 | 부록 A 완료 — `Assets/Sprites/Player/Mask/` | 그대로 소비 |

⭐ **에셋 편집이 하나도 없다.** 씬 편집 · `Renderer2D.asset` 편집 · `.inputactions` 편집 · 신규 셰이더가
전부 불필요하다(자동 발동이라 입력 액션이 없고, 렌더러 피처가 아니라 월드 오브젝트라 파이프라인
등록이 없으며, 예고 원은 기존 `Custom/RampageOutline`을 재사용한다).
**승인 항목은 리팩터 1건뿐이다** — `CanStartLightSpend()`에서 `IsActionIdle`을 뽑아 쓰는 것(§4 T-1a).

### 불일치 1의 처리 (흑백 + 슬로우)

기획안은 초월을 화면 연출(흑백)과 시간 조작(슬로우)으로 정의하는데, 이번 지시는 **플레이어 블룸 +
정보 시각화**다. 서로 배타적이지 않고 **층이 다르다** — 나중에 흑백·슬로우를 얹어도 이번 작업이
그대로 살아남는다. 다만 두 가지를 미리 짚어 둔다.

- **흑백을 나중에 켤 때**: cyan 블룸은 `VFXNoGrayscale`(레이어 15) 보호 레이어에 올라가므로
  (`PlayerBloomFx.cs:73~74`) 흑백 화면 위에서 **청록만 살아남는** 그림이 자동으로 나온다. 별도 작업 없음.
- **슬로우를 나중에 켤 때**: T-3의 예고 원은 **스케일된 시간**을 따르도록 설계했다(§5 시간축 항목).
  슬로우가 들어와도 예고와 실제 창이 어긋나지 않는다.

### 가정 (다르면 알려 주세요)

- **발동 키가 없다.** 광원이 100%가 되는 순간 자동 진입한다 — 폭주가 0에서 자동 진입하는 것
  (`PlayerController.cs:1313~1318`)과 정확히 대칭이고, 지시문의 "100%일 때 발동되어"를 그대로 옮긴 것이다.
  키 발동으로 바꾸려면 `PlayerActions.inputactions` 편집이 필요해진다(= 승인 항목이 하나 생긴다).

## 3. 수지표 — 초월이 광원 경제에 들어가는 자리

기존 값은 **하나도 바꾸지 않는다.** 소비처가 하나 더 생길 뿐이다.

| 흐름 | 값 | 위치 | 상태 |
|---|---|---|---|
| 최대치 / 시작 | 100 / 50% | `PlayerController.cs:68~70` | 무수정 |
| 적 타격 1회 | +3 | `PlayerController.cs:2234` | 무수정 |
| 적 처치 | +10 | 동일 호출부 | 무수정 |
| 패링 성공 | +25 | `PlayerController.cs:1011` | 무수정 |
| 처형 성공 | +30 (+체력 1칸) | `PlayerController.cs:1726` | 무수정 |
| 일섬 (차지 비례) | -40 | `PlayerController.cs:74` | 무수정 |
| 광원 소모 (E 홀드) | 초당 -25 | `PlayerController.cs:126` | 무수정 |
| 자아 고갈 중 (폭주) | 초당 -5 | `PlayerController.cs:121` | 무수정 |
| **초월 유지** | **초당 -6** *(신설)* | T-1 | **이번 작업** |
| 폭주 = 광원 0 | 자동 진입 / 25% 해제 | `PlayerController.cs:88` | 무수정 |
| **초월 = 광원 100%** | **자동 진입 / 70% 해제** *(신설)* | T-1 | **이번 작업** |

### 설계 의도와 그 검증

```
   광원  0 ──────────────── 25 ──────────────── 70 ──────────── 100
        │◀── 폭주 ──▶│                          │◀── 초월 ──▶│
        진입          해제                       해제          진입
        (자동)        (때려서 벌면)               (드레인·소비)  (자동)
```

- **양 끝이 상태, 가운데가 평상시**다. 자원 하나가 세 구간을 만드는 구조라 게이지 하나만 보면 된다.
- **폭주는 벌어서 탈출하고, 초월은 써서 끝난다** — 방향이 정반대라 플레이어의 행동 동기가 겹치지 않는다.
- **드레인 6/s의 근거**: 100 → 70이 정확히 **5.0초**. 자아 드레인(6/s, `PlayerController.cs:112`)과 같은 값이라
  인스펙터에서 두 상태의 체감 길이를 나란히 비교하며 튜닝할 수 있다.
- **연장의 손익분기**: 드레인 6/s를 타격(+3)으로 상쇄하려면 **초당 2타**가 필요하다. 1-2타 콤보 길이가
  각 0.4167s(`PlayerController.cs:142~143`)라 이론상 가능하지만 적중이 전제라 쉽지 않다.
  반면 **패링(+25) 1회 = 4초 연장, 처형(+30) 1회 = 5초 연장**이라 고난도 조작이 곧 지속시간이 된다.
  → 이 곡선이 의도한 것인지는 실측 후 판단한다(§9 리스크 1).

## 4. T-1. 상태 머신

### T-1a. ⭐ 진입 지연 — 액션·연출이 끝난 뒤에 들어간다

> 사용자 지시(2026-08-02): "폭주와 초월은 조건 달성 후에 바로 되지 말고, 현재 어떠한 액션 또는
> 연출이 진행이 끝난 뒤에 되는 걸로 하자."

⚠️ **이 항목만 이미 동작 중인 폭주를 바꾼다.** 나머지는 전부 신규 기능이라 회귀가 없지만,
여기는 검증까지 끝난 기존 동작(`PlayerController.cs:1316`의 즉시 진입)을 수정하는 것이라
**단계 1에서 먼저 하고 기존 `[ASSERT] rampage`로 회귀를 막은 뒤** 초월로 넘어간다.

#### 왜 필요한가

지금은 조건이 성립한 프레임에 바로 진입한다. 그래서 **처형 연출 도중·일섬 발동 도중에
폭주가 끼어들어** 카메라·애니메이션·블룸이 한 연출 안에서 두 번 갈아탄다. 특히 초월은
처형 보상(+30, `PlayerController.cs:1726`)으로 100에 도달하는 경로가 있어 이 문제가 확실히 발생한다.

#### 판정 기준 — 새 개념을 만들지 않는다

이 프로젝트엔 이미 "지금 플레이어가 자유로운가"의 정의가 있다 — `CanStartLightSpend()`
(`PlayerController.cs:1564~1568`)가 광원 소모를 시작할 수 있는지 볼 때 쓰는 목록이다.
**그 목록을 그대로 기준으로 삼는다.**

```csharp
/// 지금 아무 동작·연출 중이 아닌가. 상태 진입(폭주·초월)을 미룰지 판단하는 단일 기준.
bool IsActionIdle =>
    !isExecuting && !ilseomActive && !isCharging && !isDashing
    && !isAttacking && !isDodgeCountering && !isParrying && !isSpendingLight;
```

| 플래그 | 무엇을 점유하는가 | 위치 |
|---|---|---|
| `isExecuting` | 처형 — 무적 + 이동/공격 잠금 + 카메라 연출 | `:432` |
| `ilseomActive` | 일섬 발동 — 무적 + 충돌 무시 + 이동 연출 | `:413` |
| `isCharging` | 일섬 차지 — 블룸·게이지 점진 소모 진행 중 | `:408` |
| `isDodgeCountering` | 회피 카운터 — 슬로우모션 + 돌진 연출 | `:400` |
| `isSpendingLight` | 광원 소모 — 캐스팅(제자리 고정 + 줌인 + 지속 쉐이크) | `:436` |
| `isAttacking` · `isDashing` · `isParrying` | 공격 모션 · 대시 · 패링 모션 | `:390` `:378` `:418` |

⚠️ **`isGrounded`는 넣지 않는다.** 넣으면 공중에 떠 있는 동안 진입이 무한 연기되고,
특히 낙하 중에는 영원히 걸리지 않는다. 광원 소모가 `isGrounded`를 요구하는 건 캐스팅 고유 조건이지
"자유로움"의 일부가 아니다.

#### 예약 플래그를 두지 않는다

"조건 달성 → 예약 → 나중에 발동"이 아니라 **매 프레임 조건을 다시 본다.**

```csharp
if (currentEnergy <= 0 && IsActionIdle) StartRampage();          // 폭주
if (currentEnergy >= TranscendEnterEnergy && IsActionIdle) StartTranscend(); // 초월
```

- 대기 중에 조건이 풀리면(공격이 적중해 광원 +3, 일섬 차지로 광원 감소) **자동으로 취소된다.**
- 상태 변수가 늘지 않고, "예약해 뒀는데 조건이 사라진" 모순 케이스가 구조적으로 생기지 않는다.

#### ⚠️ 해제는 미루지 않는다 (진입만)

지시문의 "조건 달성 후에 바로 **되지** 말고"는 진입을 가리킨다고 읽었다. 해제까지 미루면 안 되는
이유가 셋 있다.

1. **사실상 영구 지연이 된다.** 폭주 해제 조건은 "광원 25% 회복"이라 **전투 중에만** 성립하는데,
   전투 중이라는 건 `isAttacking`이 계속 서 있다는 뜻이다 → `IsActionIdle`이 거의 성립하지 않는다.

### T-1b. 초월 상태 전이

```
[평상] ── currentEnergy >= 100 ──────────────▶ [초월]
[초월] ── currentEnergy <= 70 ───────────────▶ [평상]
```

- **진입에는 T-1a의 `IsActionIdle`이 함께 걸린다** — 조건이 성립해도 액션·연출 중이면 기다린다.
- **이력(hysteresis) 폭이 30**이라 폭주(0↔25)보다도 넓다. 깜빡임 위험 없음.
- **폭주와 구조적으로 동시 성립 불가** — `currentEnergy`가 0 이하이면서 100 이상일 수 없다.

### 드레인 규칙

- 정수 자원이므로 `transcendDrainAccum`에 소수점 소모분을 모았다가 1 이상에서 깎는다
  — `DrainEgo()`(`PlayerController.cs:1335~1352`)와 완전히 같은 패턴.
- ⚠️ **`isExecuting` 중에는 드레인하지 않는다.** 처형은 조작이 막힌 연출 구간이라 그동안 자원이
  닳으면 플레이어가 손해를 본다 — 자아 드레인이 이미 같은 예외를 둔다(`PlayerController.cs:1337`).
- ⚠️ **`Time.deltaTime`을 쓴다**(unscaled 아님). 히트스톱·저스트 닷지 슬로우 중에 초월만 정상 속도로
  닳으면 슬로우가 페널티가 된다. 자아·폭주 드레인과 같은 선택.

### 획득 처리 — **`AddEnergy`를 건드리지 않는다**

폭주는 획득에 0.25배를 곱하지만(`PlayerController.cs:2323`), 초월은 **사용자 결정에 따라 배율이 없다.**
`AddEnergy`가 이미 `maxEnergy`로 클램프하므로(`:2324`) 100을 넘겨 쌓이지도 않는다.
→ **`AddEnergy`에 추가할 코드가 한 줄도 없다.**

## 6. T-3. 적 미래 공격 범위 시각화 (예고형)

> 사용자 선택: "적이 Windup(예비동작)에 들어가면 창끝이 닿을 원이 나타나고, 판정 순간에 맞춰
> 안쪽부터 채워진다."

### 왜 이 데이터가 정확한가

`DummyEnemy`가 **실제 피격 판정에 쓰는 값이 이미 public으로 노출돼 있다.**

| 노출된 값 | 정의 | 위치 |
|---|---|---|
| `AttackHitPoint` | `transform.TransformPoint(spearThrustLocalPos)` = 창이 최대로 뻗었을 때의 창끝 월드 좌표 | `DummyEnemy.cs:326`, `:339~342` |
| `AttackHitRadius` | `hitRadius` (0.5) = `ResolveThrustWindow`가 `OverlapCircle`에 넘기는 그 반경 | `DummyEnemy.cs:327`, `:349` |

→ **판정 원을 다시 계산하지 않는다. 진짜 판정 원을 그대로 그린다.**
"보이는 것과 맞는 것이 다르다"는 부류의 버그가 구조적으로 불가능하다.

⚠️ 이 원은 **패링 성립 조건 그 자체**이기도 하다 — 패링은 "적 공격 범위 원 ∩ 플레이어 1타 히트박스"로
판정된다(`ASSERT_CONVENTION.md:44`). 즉 이 시각화는 **패링 타이밍·거리를 눈에 보이게 만드는 장치**다.
초월의 게임플레이 가치가 여기서 나온다.

### 타임라인 ⚠️ (2026-08-02 검토에서 정정됨)

**초안은 "판정 순간 = `thrustDuration × thrustHitNormalized`(0.102s), Recover 진입 시 예고 종료"로
잡았는데 틀렸다.** 코드상 피해가 확정되는 시점은 그게 아니다.

```
DummyEnemy.ResolveThrustWindow (DummyEnemy.cs:270~308)
  hitTime   = thrustDuration × thrustHitNormalized = 0.12 × 0.85 = 0.102s  ← 회피 인정의 기준점
  피해 확정 = hitTime + dodgeWindowPost            = 0.102 + 0.05 = 0.152s  ← TakeDamage가 불리는 순간
  thrustDuration                                                  = 0.120s
                                                     0.152 > 0.120 → 피해는 Recover 중에 확정된다
```

`DummyEnemy.cs:59~63`에 의도가 적혀 있다 — "피해는 창이 닫히는 순간에 확정된다… post를 짧게(0.05s)
잡아 피해가 확정되는 시점에도 창이 아직 거의 다 뻗은 상태(16%만 회수)로 보이게 한다."
초안대로면 **원이 판정 0.05초 전에 꽉 차고, 실제 피해 0.032초 전에 사라진다.** 예고 장치로서 치명적이다.

**정정된 타임라인:**

```
적이 사거리(2.4) 진입
        │
   [Windup 0.25s]           [Thrust 0.12s]      [Recover 0.032s]
   ○ ────────────────────▶ ◕ ──────────────▶ ◕ ──▶ ● 피해 확정!
   윤곽만 뜸               안쪽부터 차오름           터짐(1.25배 팽창) + 사라짐
   progress 0              0.622                    progress 1

   총 예고 시간 = windupDuration + hitTime + dodgeWindowPost
                = 0.25 + 0.102 + 0.05 = 0.402초
   Thrust 시작 = 0.25 / 0.402 = progress 0.622
```

- **예고는 Recover 구간까지 이어진다.** 그 시점에도 창은 84% 뻗어 있어 시각적으로 여전히 "찌르는 중"이다.
- 참고: 회피 인정 창은 `hitTime - dodgeWindowPre` = **-0.018s**, 즉 Thrust 시작 시점에 이미 열려 있다.
  → 회피·패링 가능 구간 = progress **0.622 ~ 1.0**. 이 구간을 링에 눈금으로 표시하는 건 이번 범위 밖.

### T-3a. `DummyEnemy`에 진행률 하나만 추가 (읽기 전용)

#### ⚠️ 왜 스캔을 두 층으로 쪼개는가 (2026-08-02 검토에서 정정)

초안은 `RampageVisionFx`의 0.25s 스캔을 그대로 복제했다. 그건 **폭주라는 지속 상태**에 맞춘 값이다.
예고는 **0.402초짜리 단발 이벤트**라 같은 주기로 보면 최대 0.25초 늦게 떠서 **창의 62%가 날아간다.**

→ **컬링(반경 안의 적 목록 수집)만 0.25s**로 두고, **예고 진행률 평가는 캐시된 목록에 대해 매 프레임**
수행한다. 목록이 보통 1~5개라 float 프로퍼티 읽기 몇 번이라 비용은 무시할 수준이다.
같은 이유로 적이 파괴됐을 때의 정리도 매 프레임 잡혀 누수 창이 좁아진다.

- **초월이 아닐 때는 예고 0개** (평상시·폭주 중 모두)
- 초월 해제 → 예고 오브젝트 **0개**, `TranscendVisionFx` 파괴

### ⚠️ 드레인은 초가 아니라 **프레임 누적**으로 검증한다

"5초 후 70"처럼 초 단위로 재는 검증은 이 프로젝트에서 이미 실패한 방식이다 —
선행 계획서 §9 리스크 11: 원격 에디터의 프레임 튐 때문에 "검증은 초가 아닌 **프레임 수 루프**로".

→ N프레임을 돌리며 `Σ Time.deltaTime`을 누적하고, **기대 감소량 `6 × Σdt`와 실제 감소량을
±1(정수 누적기 오차)로 대조**한다. 같은 방식이 자아 드레인·광원 소모에도 그대로 적용된다.

### 기존 채널 회귀 검사

`rampage` · `ego` · `light_spend` · `player_hud` · `parry_timing` · `dummy_attack` · `game_data`

- **`rampage`가 이번 작업의 최대 회귀 위험이다** — T-1a가 검증 끝난 진입 조건을 바꾼다.
  ⚠️ 단 **판정 항목은 무수정 통과해야 하지만 시나리오 코드는 손봐야 한다**(§9 리스크 9 — 1719행이
  `currentEnergy = maxEnergy`라 이제 초월이 끼어든다). "판정은 그대로, 셋업만 수정"이 원칙이다.
- **`dummy_attack`·`parry_timing`** — T-3a가 `DummyEnemy`를 건드리므로 판정 타이밍이
  한 프레임도 변하지 않았음을 이 두 채널로 증명한다.
- **`light_spend`** — T-1a의 리팩터(`CanStartLightSpend`)가 승인되면 이 채널이 그 회귀를 잡는다.

## 13. 초월 진입 순간 연출 — 조사 + 설계안 (2026-08-02 후속, 구현 전 계획 단계)

사용자 지시: "초월 진입 vfx 관련해서 조사 및 계획 수립." §11(c)에서 미룬 항목을 다시 요청받아
폭주의 대응 시스템(`RampageHeartbeatFx`)을 전부 조사하고, 그 위에 초월용 설계안 3가지를 세웠다.
**아직 구현하지 않았다** — 설계안 확정 후 다음 세션(또는 이 세션 후속)에서 구현.

### 13-1. 조사 — 폭주(`RampageHeartbeatFx`)가 이미 갖고 있는 것

`Assets/Scripts/VFX/RampageHeartbeatFx.cs`, `StartRampage()`(`PlayerController.cs:1574~1615`)에서
`RampageHeartbeatFx.Begin(transform, sectionCamera, focusPulseRampIn, focusPulseHold,
focusPulseRampOut)` + `RampageGlitchFlicker()` 두 줄로 호출된다.

| 구성 요소 | 값·메커니즘 |
|---|---|
| 화면 펄스(박동) | 전체화면 `Image`(오버레이 캔버스) 알파를 lub(0.30)→dub(0.16) 2단으로, 강한 박동 1회 + 0.20초 후 약한 박동(세기 0.6) 1회. `FlashColor=(0.55,0.02,0.04)` |

전부 `Time.unscaledDeltaTime` 기반(히트스톱·슬로우 중에도 정상 재생), `focusToken`/`sustainFocusToken` 같은
세대 카운터로 중복 호출을 안전하게 무력화하는 패턴을 공유한다.

**테마**: 폭주 = 빛 **흡수** + 이성 **붕괴** → 연출은 박동(불규칙한 심장)·글리치(시스템 오류)·
적색(경고)으로 **혼란**을 표현한다.

### 13-2. 현재 초월 진입에 있는 것 / 없는 것

`StartTranscend()`(`PlayerController.cs:1645~1682`)에 이미 있는 것:
- 빛 흡수 버스트 1회(`LightPixelFx.SpawnAbsorb`, 진입 전용) — 이번 세션 1차 피드백에서 추가

**없는 것**: 폭주의 "펀치"에 대응하는 것 — 카메라가 반응하지 않고, 화면이 반응하지 않고, 시간이
반응하지 않는다. 광원이 100%를 채우는 그 순간이 그냥 "블룸이 조용히 켜짐"으로 지나간다. 이게
§11(c)가 원래 지목했던 빈 자리이고, 이번 조사·설계의 대상이다.

### 13-3. 세계관 근거와 설계 방향

`세계관_및_고유명사_설정.md:66`: "초인적인 **가속력**을 얻게 되며, **찰나의 시간** 속에서 움직이는
듯한 **정교하고 빠른** 속도전을 구사합니다."

폭주와 초월은 세계관상 정확히 반대 극단이므로(1부 §1-1), 진입 연출도 **정반대 감각**이어야 한다:

| | 폭주 | 초월 |
|---|---|---|
| 자원 방향 | 흡수 | 방출 |
| 정신 상태 | 이성 붕괴 | 초인적 가속·정교함 |
| 연출 언어(기존) | 박동(불규칙) · 글리치(오류) · 적색(경고) | ? ← 이번에 정할 것 |
| 제안 | — | 스냅(단발) · 클린 플래시(오류 없음) · cyan(이미 확정색) |

**글리치(`ScreenGlitchFx`)는 재사용하지 않는다** — "시스템 오류·붕괴"라는 의미가 이미 폭주·자아
고갈에 확실히 붙어 있어서, 초월(정교함)에 가져오면 테마가 충돌한다. 카메라 펀치(`FocusPulse`)와
링 생성 절차는 색만 다르면 의미가 중립적이라 그대로 재사용 가능.

### 13-4. 설계안 3가지 (택 1, 확정 필요)

**A안 — 미니멀 스냅**
카메라 `FocusPulse` 1회(줌만) + cyan 플래시 1회. 링 없음, 시간 효과 없음.
- 장점: 가장 저비용, "절제된 정교함"에 가장 가까움.
- 단점: 존재감이 약해 "광원이 100%가 됐다"는 순간이 잘 안 느껴질 수 있다.

**B안 — 가속 릴리즈 (권장)**
빛 흡수 버스트가 도착하는 타이밍(스폰 후 약 0.4~0.5초, `LightPixelFx.Spawn`의 개별 픽셀 수명
0.35~0.55초 범위와 맞춘다)에 맞춰 "방출" 비트 1회 발동:
1. cyan-화이트 플래시 1회(즉각, rise 0.02s/fall 0.06s — 폭주와 같은 곡선, 색만 다름)
2. 바깥으로 팽창하는 cyan 링 1회(`RampageHeartbeatFx`와 같은 절차 생성 기법 재사용, 폭주보다
   빠르고 타이트하게: 0.25초, 스케일 0.3→2.5)
3. 카메라 `FocusPulse` **단발**(줌만, 폭주 세기의 절반 정도) — 폭주처럼 두 번 박동하는 대신
   "한 번에 튕겨나가는" 단일 펀치
4. 글리치 없음, 슬로우모 없음
- "모아서(흡수) → 터뜨린다(방출)"는 서사가 이미 있는 흡수 버스트와 자연스럽게 이어진다.
- 폭주 대비 구성 요소가 적어(2박동→1박동, 글리치 제거) "정교함"이 수치로도 드러난다.

**C안 — 찰나의 시간 (세계관에 가장 충실, 사용자 확인 필요)**
B안에 아주 짧고 강한 시간 정지를 방출 비트 직전에 삽입: `Time.timeScale` 0.05~0.1을
0.08~0.12초만 유지한 뒤 0.1초 내로 정상 복귀.
- "찰나" 그 자체를 체감시키는 장치 — 세계관 문장을 가장 직접적으로 연출로 옮긴 안.
- 폭주의 슬로우모(0.5배·0.3초·"박동이 느려진 세상 속에서 도드라짐")와는 톤이 다르다 — 이쪽은
  "시간이 멈췄다가 순식간에 풀리는" 스냅이라 배율이 훨씬 극단적이고 훨씬 짧다.
- ⚠️ **리스크**: §11(a)에서 "슬로우모는 이번 범위 제외"라고 이미 결정한 것과 형태는 다르지만
  (그건 "상시" 슬로우, 이건 "진입 0.1초"짜리 스파이크) 언뜻 같은 항목처럼 보일 수 있어 착수 전
  사용자 확인이 필요하다고 판단해 A/B안과 함께 제시한다.

### 13-5. 기술 구현 개요 (B안·C안 공통, 확정되면 그대로 착수)

- 신규 파일 `Assets/Scripts/VFX/TranscendBurstFx.cs` — `RampageHeartbeatFx`와 같은 구조(정적
  `Begin`, 자기 파괴, `Time.unscaledDeltaTime` 기반 타이밍, `Custom/PlayerBloomOverlay` 재사용).
  신규 셰이더 없음.
- 링 텍스처는 `RampageHeartbeatFx.GetRingSprite()`와 같은 절차(64×64, 밴드)를 cyan
  (`TranscendBloomTint`, `PlayerController.cs`에 이미 정의됨)으로 복제.
- 카메라 펀치는 `SectionCamera.FocusPulse` 그대로 재사용 — 신규 카메라 API 불필요.
- `StartTranscend()`의 `LightPixelFx.SpawnAbsorb(...)` 호출 바로 다음 줄에
  `TranscendBurstFx.Begin(transform, sectionCamera, ...)` 한 줄 추가(방출 비트의 딜레이는 이
  컴포넌트 내부 코루틴이 자체적으로 갖는다 — `StartTranscend()`를 더 건드릴 필요 없음).
- **승인 필요 항목 없음** — 신규 파일 1개 + 기존 메서드에 한 줄 추가뿐, 검증된 기존 로직 변경 없음.

### 13-6. 검증 계획
