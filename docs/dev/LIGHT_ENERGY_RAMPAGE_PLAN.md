## 3. A. 광원(빛 에너지) 시스템 설계

### A-0. 자원 모델 (수지표)

기존 값은 그대로 두고 **획득 하나만 추가**한다. 기준선: `일섬 1회 = 패링 2회 = 오브 4개`.

| 흐름 | 값 | 위치 | 근거 |
|---|---|---|---|
| 최대치 | 100 | `PlayerController.cs:68` | — |
| 시작 | 50% | `PlayerController.cs:70` | 충전·소모가 둘 다 보이도록 |
| 패링 성공 | **+25** | `PlayerController.cs:880` | `기능_구현_명세서.md:64` |
| 처형 성공 | **+30** (+체력 1칸) | `PlayerController.cs:1339` | `기능_구현_명세서.md:69` |

| ~~폭주 발동 하한 50~~ | **폐기** | — | ⬇ |

> ⚠️ **폭주 규칙이 바뀌었다(2026-08-01 사용자 지시).** "모은 빛 에너지를 **소모하여** 폭주"
> (`기능_구현_명세서.md:78~79`)로 만들었던 것을 **"광원이 0이 되면 자동으로 폭주"** 로 뒤집었다.
> 폭주는 이제 소비처가 아니라 **자원이 바닥난 상태 그 자체**다. 해제는 다시 빛을 얻는 것뿐이다.
> 이 규칙이 시야 제한(§4 B-2)과 정확히 맞물린다 — 몸 안의 빛이 없으니 앞이 안 보인다.
> 그래서 상위 소비처는 일섬(-40)과 광원 소모(초당 -25) 둘만 남고, **바닥까지 쓰는 것 자체가
> 폭주라는 리스크/보상**이 된다.

> **설계 의도**: 잡몹 1마리(타격 3회 + 처치) ≒ **+19**라 적 2마리면 일섬 1회. 폭주(50)와 방출(초당 25)이 상위 소비처가 되어 명세서의 "모은 빛 에너지를 소모하여"라는 선택 구조가 성립한다.
> ⚠️ 방출이 체력 회복 수단이 되면서 **"때리면 회복"이 순환할 수 있다** — §9 리스크 6, §10 질문 2 참조.

### A-1. 빛 조각(Light Orb) — 드랍·픽업 *(→ §5 C-1로 대체됨)*

> ⚠️ **이 절은 2026-08-01 사용자 지시로 §5 C-1에 흡수됐다.** 획득 트리거가 "적 처치"에서
> "타격 · 처치 · 오브젝트 파괴 · 상호작용" 4종으로 늘고, 연출이 "튀어오르는 오브"에서
> **"포물선을 그리며 흡수되는 작은 픽셀들"** 로 바뀌었다. 아래는 최초 설계 기록으로만 남긴다.

**신규 파일** `Assets/Scripts/Light/LightOrb.cs` (단일 파일, 프리팹·텍스처 의존 0)

```
public static void Drop(Vector3 origin, int count, int valueEach = 10)
```

| 단계 | 동작 | 파라미터 |
|---|---|---|
| 1. 스폰 | 사망 지점에서 위쪽 부채꼴로 튀어오름 | 초기 속도 3~5, 각도 ±40° |
| 2. 안착 | 중력 낙하 + 감쇠, 짧게 튐 | `Rigidbody2D`, drag 2 |
| 3. 유도 | `magnetDelay`(0.35s) 후 플레이어를 향해 가속 | 유도 반경 6, 가속 18/s² |
| 4. 흡수 | 접촉 시 `AddEnergy(+value)` → 흡수 VFX → 자기 파괴 | 접촉 거리 0.4 |
| 5. 만료 | `lifetime`(12s) 초과 시 깜빡이다 소멸 | 누수 방지 |

- **드랍 훅은 1곳**: `DummyEnemy.Die()` (`DummyEnemy.cs:431`)에 `LightOrb.Drop(transform.position, orbDropCount)` 한 줄. `DummyEnemy`에 `public int orbDropCount = 1;` 필드 추가.
- ⚠️ **더미는 `respawnDelay` 후 부활한다**(`DummyEnemy.cs:441`). 부활할 때마다 오브를 뿌리면 무한 파밍이 되므로, 테스트용 더미는 **드랍 카운트 기본 1 + 인스펙터에서 0으로 끌 수 있게** 한다.
- **에너지 만충일 때**: 오브는 그대로 흡수시키되 초과분은 버린다(`AddEnergy`가 이미 클램프). 흡수 자체를 막으면 화면에 오브가 쌓여 지저분해진다.

### A-2. 일섬 에너지 게이팅

## 4. B. 폭주(Rampage) 마감 설계

### B-1. 입력 정식화 *(승인 필요 — 에셋 편집)*

- `Assets/PlayerActions.inputactions`의 `Player` 맵에 `Rampage`(Button) 추가 — 바인딩 `<Keyboard>/q` + 게임패드 `<Gamepad>/buttonNorth`.
- `PlayerController`에 `void OnRampage()` 콜백 추가(`PlayerInput`의 SendMessages 방식은 기존 `OnJump`/`OnDash`와 동일).
- ⚠️ **기존 Q 폴링은 지우지 않고 폴백으로 남긴다** — 이 프로젝트엔 "SendMessages가 Button의 `canceled`를 안 보내 짧은 점프가 죽은" 선례가 있다(`task.md` 미결 #6). 정식 액션이 실측으로 확인되면 그때 폴링을 제거한다(삭제는 규칙 4 → 별도 승인).

### B-2. 시야 제한 (이번 폭주 작업의 핵심)

> 사용자 지시(2026-07-31): "폭주 상태의 시야 제한 — 아주 근처만 보이고 나머지는 암흑,
> 적은 실루엣 아웃라인이 보이고, 타일맵은 아웃라인으로 발판들만 보임."

#### 왜 이게 맞는 설계인가 (검토 의견)

- **세계관을 게임플레이로 옮긴다.** `세계관_및_고유명사_설정.md:64`의 "이성은 붕괴하지만"이 지금까지 유일하게 구현되지 않은 서술이었다(§1 대조표 #11). 시야 제한이 정확히 그 대응물이다.
- **폭주에 없던 리스크를 만든다.** 현재 폭주는 피해 2배·넉백 면역·피격 시 체력 대신 에너지 소모라 **사실상 순수 상향**이고, 비용이 에너지뿐이다. 시야 제한이 들어가면 "강해지는 대신 앞이 안 보인다"는 진짜 트레이드오프가 생겨 `기능_구현_명세서.md:79`의 "모은 빛 에너지를 소모하여"라는 선택 구조가 실제로 성립한다.
- ⚠️ **하드코어 플랫포머에서 시야 제한은 낙사 위험을 급격히 올린다.** 그래서 사용자가 말한 "타일맵 발판 아웃라인"이 필수 완화책이다 — 이게 없으면 폭주가 "쓰면 손해"인 기능이 된다.

### C-2. 광원 소모 (E 홀드)

#### 상태 머신

```
[대기] --E 누름(조건 통과)--> [방출 중] --E 뗌--------------> [대기]
                                  |--피격------------------> [중지] (E 재입력 필요)
                                  |--에너지 10% 진입(첫 1회)-> [중지] (E 재입력 필요)
                                  |--에너지 0--------------> [대기]
```

**시작 조건**: `currentEnergy > 0` AND `!isRampaging`(C-5) AND `!isExecuting` AND `!ilseomActive` AND **`isGrounded`**(캐스팅이라 지상 한정 — 아래 참조)

#### 수치

| 항목 | 값 | 비고 |
|---|---|---|
| 소모 속도 | **초당 25** (maxEnergy 100 기준 = 초당 25%) | 100%를 4초에 소진 |
| 체력 회복 | **누적 25 소모마다 +1칸** | 100% 전량 방출 = 최대 4칸 회복 |
| 실드 생성 | 체력이 **이미 최대**인 상태에서 25 소모 누적 시 1개 | 아래 규칙 참조 |
| 10% 강제 중지 | `currentEnergy`가 10 이하로 **내려가는 순간 1회만** | 재입력하면 0까지 계속 방출 가능 |

- **누적 소모 카운터**로 처리한다 — 폭주 드레인이 쓰는 `rampageDrainAccum` 패턴(`PlayerController.cs:1188~1196`)과 동일. 에너지가 정수라 소수점 소모분을 모았다가 임계에서 한 번에 처리한다.
- **10% 중지는 "구간 진입 시 1회"** 다. `_lowWarningFired` 플래그로 관리하고, 에너지가 10을 넘게 회복되면 플래그를 리셋한다(그래야 다음 번에도 경고가 작동).

#### 1회용 실드 — 기존 패링 실드를 그대로 재사용

**새로 만들 것이 거의 없다.** `PlayerController`에 이미 다음이 있다:

| 기존 자산 | 위치 | 역할 |
|---|---|---|
| `SpawnParryShield()` | `PlayerController.cs:918` | 실드 생성(기존 실드가 있으면 파괴 후 재생성) |
| `parryShieldActive` | `PlayerController.cs:374` | 판정 상태(연출과 분리) |
| `TryConsumeParryShield()` | `PlayerController.cs:933` | 1회 소모 + 깨짐 연출 |
| `HasParryShield` | `PlayerController.cs:942` | 보유 여부 |

- **"1개 초과 불가 · 패링 실드와 중복 불가"가 자동으로 성립한다** — 같은 `parryShieldActive` 플래그 하나를 공유하므로 구조적으로 2개가 될 수 없다.
- 방출 실드 생성 시 **`HasParryShield`가 true면 생성하지 않는다**(패링 실드를 덮어써 리셋시키지 않도록). `SpawnParryShield()`는 기존 것을 파괴하고 다시 만들기 때문에 그대로 부르면 안 된다 — **가드를 새로 둔다.**

#### 방출 중 잠금

- **Idle 애니메이션 고정**: 일섬의 `RestoreAnimAfterIlseom()`이 쓰는 "고아 상태 복원" 패턴을 따른다. 방출 시작 시 Idle 상태로 강제 전환·고정, 종료 시 `try/finally`로 반드시 복원한다(이 프로젝트에서 반복 검증된 안전망).
- ✅ **제자리 고정 = 캐스팅(2026-08-01 사용자 결정)**: 이동·점프·대시를 전부 잠근다. Idle 모션 고정과 앞뒤가 맞고, "멈춰서 빛을 끌어올린다"는 연출이 명확해지며, **"피격당하면 끊긴다"는 규칙이 캐스팅 구조와 자연스럽게 이어진다.**
  - 잠금은 **일섬·처형과 같은 상태 플래그**(`isSpendingLight`)로 하고 이동 입력 처리부에서 조기 반환한다. 물리 속도는 0으로 묶는다(`PlayerController.cs:512`의 `ilseomActive` 처리와 같은 패턴).
  - ⚠️ **공중에서 시작하면?** 중력까지 끄면 공중 부양이 되고, 그대로 두면 낙하하며 캐스팅한다. **지상에서만 시작 가능**하게 막는 것을 기본안으로 한다(캐스팅류의 표준). 공중 캐스팅을 허용하려면 별도 지시.

### C-4. ⭐ 모든 블룸을 마스크 기반으로 전환

**이번 지시에서 가장 파급이 큰 항목이다.** 부록 A의 발광 마스크가 여기서 소비된다.

#### 현재 방식의 한계

`PlayerBloomOverlay.shader:17`의 `_Flatten`은 **알파 실루엣 전체**를 균일하게 발광시킨다. 그래서 일섬 차지 때 캐릭터 전체가 통으로 빛난다 — 눈·글리치만 빛나야 할 곳까지 포함해서.

#### 변경안

- `PlayerBloomOverlay.shader`에 **`_EmissionMask` 텍스처 프로퍼티 추가** → 마스크의 흰 픽셀만 발광, 검은 픽셀은 원본 그대로.
- **UV가 저절로 맞는다**: 마스크 시트는 원본과 **크기·프레임 배치가 완전히 동일**하다(부록 A-2 실측). 따라서 `_MainTex`를 샘플링한 UV를 그대로 `_EmissionMask`에 쓰면 프레임이 바뀌어도 자동으로 대응된다. **프레임별 배선이 전혀 필요 없다.**
- 스프라이트가 아니라 **시트 텍스처**를 마스크로 물린다(`sr.sprite.texture`에 대응하는 마스크 시트 1장).

#### 이 변경의 수혜 범위 (한 번 고치면 전부 적용)

| 블룸 | 색 | 상태 |
|---|---|---|
| 일섬 차지·발동 | 청백 (`PlayerBloomOverlay.shader:12` 기본값) | 기존 — 마스크만 적용 |
| **광원 소모** | 청백 | C-2 신규 |
| **폭주 상시** | 붉은색 `RampageCore` | C-5 신규 |

- ⚠️ **`.shader` 편집이 필요하다 → 승인 필요.** 과거 세션에서 `.shader`/`.mat` 편집이 권한으로 막혀 우회한 이력이 있다(`task.md` 처형 아웃라인 절). 이번엔 **우회가 불가능하다** — 마스크 샘플링은 셰이더 안에서만 가능하다.
- **선행 조건**: 부록 A의 마스크 14장 생성이 먼저 끝나야 한다. 마스크가 없는 시트는 발광이 통째로 사라지므로, **전량 생성 완료 전에는 이 전환을 켜면 안 된다.**
- **폴백**: `_EmissionMask`가 비어 있으면 기존 `_Flatten` 동작을 그대로 쓴다(마스크 누락 시 회귀 방지).

## 6. VFX 공통 규약 (이 프로젝트에서 이미 검증된 것)

새 VFX는 아래를 따른다. 전부 과거 세션의 실패에서 나온 규칙이다.

1. **런타임 생성 · 씬 미저장** — 프리팹/텍스처 의존 0. `PlayerHudUI`, `DashAfterImage`, `EnemyExecutionGlowFx` 전부 이 방식.
2. **원본 `SpriteRenderer`를 건드리지 않는다** — 실루엣을 한 겹 더 그린다. 머티리얼 복원 실패 사고를 구조적으로 차단(`PlayerBloomFx` 주석).
3. **셰이더/머티리얼 에셋을 새로 만들지 않는다** — `Shader.Find` + 런타임 머티리얼 + `SetColor/SetFloat`. (`.shader`/`.mat` 편집은 과거 세션에서 권한으로 막힌 이력이 있다.)
4. **두께·크기는 월드 단위로** — 텍셀(PPU) 단위로 잡았다가 화면에서 서브픽셀로 사라진 버그가 있었다(`task.md` 처형 아웃라인 건).
5. **시간축은 `unscaledDeltaTime`** — 히트스톱·슬로우모션 중에도 UI/픽업은 정상 속도로. 원격 에디터 프레임 튐 대비 `maxSmoothDelta`(0.05) 상한도 함께.
6. **`VFXNoGrayscale` 레이어** — 흑백 연출 중에도 색을 유지해야 하는 것만.
7. **종료 시 자기 파괴 + 누수 검사** — 폭주 종료·사망·씬 정지 어느 경로로 끝나도 오브젝트가 남지 않아야 한다.

### ⚠️ 영상 판정기는 1차 증거로 쓰지 않는다

이 프로젝트의 `report_video.py` 판정기는 **정적인 색·얇은 디테일 변화에 반복적으로 FAIL**을 냈다 — 처형 아웃라인 3연속 FAIL, HUD 바/칸 2연속 FAIL. 그런데 두 건 다 **엔진 픽셀 실측·스크린샷으로는 정상**임이 증명됐다(`task.md` 해당 절).

**시야 제한은 이 한계가 더 심하다** — 어두운 화면은 유튜브 압축(밴딩·블록 노이즈)에 특히 취약하고, 아웃라인은 얇은 색 경계라 판정기가 3연속 FAIL을 낸 바로 그 종류다.

따라서 **B-2의 1차 증거는 `execute_code`의 `RenderTexture` 픽셀 판독**으로 삼는다:

# 부록 A. 발광(에미션) 마스크 자동 생성 계획

> 사용자가 `mask/`에 수작업 마스크 3장을 올려둔 것을 원본과 픽셀 교차 대조해 **규칙을 역산**했다.

## A-1. 역산한 규칙 (실측으로 확정)

```
발광(흰색 255,255,255)  ⟺  알파 ≥ 16  AND  (B - R) ≥ 40
그 외(몸체 · 흰 하이라이트 · 투명)  →  검정 (0,0,0), 알파 255
```

- 출력 형식: **원본과 동일 크기**, 완전 불투명(알파 255), 흑백 2색. 투명 영역도 검정으로 채운다.
  (사용자 수작업 마스크 3장에서 실측한 형식 그대로)

### 임계값 40의 근거 — 경계선 색이 **하나도 없다**

원본 17장 통합 팔레트는 12색뿐이고, `B-R` 값이 **0~9 아니면 72~135**로 갈린다. 그 사이가 통째로 비어 있어
임계값을 **10~70 어디에 둬도 결과가 같다.** 전 시트 borderline 픽셀 **0개**.
